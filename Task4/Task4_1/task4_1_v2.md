## 2. Обоснование приоритета внедрения Circuit Breaker

Паттерн **Circuit Breaker** критически важен и приоритетен для внедрения на контуре **BFF ➜ 1С («Полисы»)**.

### Почему для 1С, а не для Платёжного шлюза:
1. **Защита хрупкого монолита:** Платёжный шлюз — это высокомасштабируемая внешняя система, устойчивая к нагрузкам. 1С — это внутренний legacy-монолит, который «ложится» при превышении 50 RPS. Circuit Breaker необходим, чтобы спасти 1С от окончательного падения под лавиной запросов.
2. **Наличие полноценного бизнес-fallback:** Для 1С есть понятная стратегия деградации — временно поверить пациенту на слово, проверив полис позже. Для платёжного шлюза Circuit Breaker бесполезен при таймауте: если заблокировать запросы, мы просто не сможем принимать деньги.

### Механизм работы Circuit Breaker при Cache Miss:
При деградации кеша Redis BFF начнет слать синхронные запросы в 1С. 1С превысит свой лимит в 50 RPS и зависнет.

* **Состояние CLOSED (Закрыт):** Запросы при Cache Miss идут в 1С. Предохранитель считает процент ошибок и долгих ответов (> 2 секунд).
* **Состояние OPEN (Открыт):** Если 50% запросов к 1С упали по таймауту, Circuit Breaker размыкается. BFF физически перестает перенаправлять Cache Miss запросы в 1С, мгновенно включая стратегию Fallback (временно доверять и записывать всех подряд без проверки). Это дает 1С время на  восстановление.
* **Состояние HALF-OPEN (Полуоткрыт):** По истечении тайм-аута в 10с предохранитель пропускает 5 тестовых запросов в 1С. Если все прошли успешно — система возвращается в статус CLOSED. Если хотя бы один завис — контур снова разрывается (OPEN).

## 3. Архитектурное решение для снижения нагрузки на 1С

Для снижения нагрузки на 1С применяется паттерн **Data Replication (Push-кэширование)** на базе распределенного кэша **Redis Cluster**.

### Как это решение разгружает 1С:
1. **Уход от схемы Pull к схеме Push:** Вместо того чтобы BFF дергал 1С при каждом поиске или записи пациента (создавая тысячи RPS), сама система 1С по расписанию (например, ночью в 03:00) выгружает слепок всей базы действующих полисов ДМС напрямую в Redis Cluster.
2. **Событийная дельта:** При оформлении нового полиса в течение дня 1С точечно отправляет одно короткое событие обновления в Redis.
3. **Результат:** 1С полностью изолирована от онлайн-трафика мобильного приложения. BFF Service проверяет лимиты ДМС из оперативной памяти Redis за несколько миллисекунд, гарантируя выполнение NFR (отклик < 1 сек), а нагрузка на 1С падает практически до нуля.
