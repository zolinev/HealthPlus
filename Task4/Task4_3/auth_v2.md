# Архитектура аутентификации и авторизации «Здоровье+»

Процесс разделен на два изолированных этапа: получение прав доступа и выполнение защищенных запросов.

### 1. Этап входа и авторизации (OAuth 2.0 + PKCE)
Вход мобильного приложения (МП) выполняется по стандарту **Authorization Code Flow с расширением PKCE** для защиты от перехвата токенов:

1. **Генерация секрета:** МП создает локальный секрет `code_verifier` и отправляет его хэш (`code_challenge`) на сервер авторизации (IdP).
2. **Ввод учетных данных:** IdP отображает клиенту защищенную форму ввода логина, пароля и второго фактора (2FA)
3. **Выдача токенов:** В случае успешной проверки IdP возвращает в МП временный код авторизации `authorization_code`. МП вызывает IDP, передавая `authorization_code` и в явном виде  `code_verifier`. IDP создает хеш из `code_verifier` и если он совпадает с изначально переданным `code_challenge`, IDP возвращает в МП токены (**Access JWT** и **Refresh Token**)

### 2. Этап выполнения авторизованного запроса к API
1. **Защита транспорта (MitM-protection):** Перед отправкой данных МП выполняет **Certificate Pinning** (проверку слепка публичного ключа шлюза) и валидацию сертификатной цепочки. При несовпадении ключей связь немедленно разрывается.
2. **Защита контура (mTLS):** Шлюз извлекает из JWT `client_id`, удаляет сырой JWT и проксирует запрос в BFF, передавая `client_id` во внутреннем HTTP-заголовке . Связь между шлюзом и BFF защищена взаимным шифрованием **mTLS** 
3. **Контроль доступа на BFF:** Сервис BFF принимает запрос, извлекает `client_id` из безопасного внутреннего заголовка и на этапе проверяет, что данные соответствуют клиенту. Это гарантирует, что пациент увидит только свои записи.
