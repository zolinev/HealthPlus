# 2. Rate Limiting

| Тип запроса | Лимит (Rate Limit) | Действие при превышении |
| :--- | :--- | :--- |
| **Публичный запрос:** Поиск врачей | 100 запросов в минуту с одного IP-адреса и/или 30 запросов в минуту с одним FingerPrint (или с одной куки для Веба). | Gateway блокирует запрос с кодом **HTTP 429 Too Many Requests** и добавляет в **header Retry-After 60**. В коде необходимо предусмотреть обработку этой ошибки и запрет пользователю на повторение запросов в течение заданного периода |
| **Авторизованный запрос:** Создание записи к врачу | **10 запросов в минуту** на один client_id (из JWT) + до **100 запросов в сутки**. | Gateway блокирует запрос с кодом **HTTP 429 Too Many Requests** и добавляет в **header Retry-After 60**. В коде необходимо предусмотреть обработку этой ошибки и запрет пользователю на повторение запросов в течение заданного периода |



# 3. Меры защиты каналов передачи данных

1. **Шифрование TLS 1.3:** Весь трафик шифруется по протоколу TLS 1.3. Слабые шифры и старые протоколы (TLS 1.0, 1.1) полностью отключены.
2. **Защита через WAF:** Перед API Gateway разворачивается Web Application Firewall для автоматической фильтрации сетевых атак, сигнатур OWASP Top 10 и попыток SQL-инъекций.
3. **mTLS для внутренних сервисов** Все сервисы общаются между собой только с использованием mTLS. Вызовы без шифрования (HTTP, AQMP) запрещены. Каждому контейнеру выпускается свой сертификат
4. **Certificate Pinning**: Для предотвращения атак класса Man-in-the-Middle и перехвата персональных/медицинских данных на стороне пользователя, в код мобильного приложения встраивается механизм Certificate Pinning. Приложение сверяет хэш публичного ключа  сертификата, полученного от API Gateway, с доверенным эталоном. Если на устройстве пользователя установлен кастомный корневой сертификат (например, вредоносное ПО или прокси-фильтр провайдера), несмотря на доверие к нему со стороны ОС, приложение зафиксирует подмену, разорвет соединение и заблокирует отправку медицинских данных.
5. **Валидация сертификатной цепочки (Chain Validation)**: Мобильный клиент принудительно выполняет полную проверку всей цепочки сертификатов шлюза до доверенного корневого Удостоверяющего Центра (CA). Дополнительно на шлюзе и клиенте настраивается проверка статуса отзыва сертификатов в реальном времени с использованием протокола OCSP (Online Certificate Status Protocol), что исключает использование скомпрометированных ключей.
